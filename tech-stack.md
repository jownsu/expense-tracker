## Backend

Express + Postgres + **Prisma** (ORM + migrations). This is the side to teach as we go.

- **Validation** — Zod on request bodies.
- **Authorization** — every query scoped to the authenticated user's id in the API layer
  (no row-level security; enforced in application code).
- **AI secrets** (v2) live on the Express server, never the client.
- **Structure** — one repo: `client/` (React) + `server/` (Express), separate
  `package.json` each.

## Auth — decision

You asked whether `next-auth` or Auth.js fits. We first chose Auth.js, then **switched to
Better Auth** early in Phase 2 (before anything was built on top of the session). Findings:

| Option | Verdict |
|---|---|
| **`next-auth`** | ❌ No. It's coupled to Next.js (its API routes/server). We dropped Next, so it doesn't apply. |
| **Auth.js (`@auth/express`)** | ⚠️ Works, and is what we started with. Framework-agnostic evolution of NextAuth with an Express integration + Prisma adapter + Google provider — but the Express integration has thin docs and weaker TypeScript ergonomics. |
| **Better Auth** | ✅ **Chosen.** TypeScript-native, owns its own schema cleanly (generated via its CLI), first-class Express integration (`toNodeHandler`) and React client (`createAuthClient` / `useSession`). Less glue code than Auth.js on this exact stack. |
| **Hand-rolled** | ✅ Most learning, most work. Verify the Google ID token server-side and issue a signed httpOnly cookie yourself. Skipped — the learning budget goes to the API/DB layer. |

**Decision: Better Auth** with the Google social provider and the Prisma adapter
(`better-auth/adapters/prisma`). We swapped off Auth.js because Better Auth's Express + Prisma
DX is cleaner and its schema/types are first-class — and doing it early cost almost nothing.

What it brings in:
- Adds Better Auth's own Prisma models — `User`, `Session`, `Account`, `Verification` — to
  the schema (generated by `npx @better-auth/cli generate`). Our app models (`envelopes`,
  `months`, …) FK to `User.id` as the owner. Note `User.id` has no DB default: Better Auth
  generates ids itself.
- Env: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`.
- Routes live under `/api/auth/*`; the handler is mounted with `toNodeHandler(auth)` **before**
  `express.json()` (the body parser would otherwise consume the request stream and hang auth).
- Google callback URL: `<API_URL>/api/auth/callback/google` (register it in Google Cloud Console).

Still worth understanding — and since it's backend, I'll coach it: how the adapter persists
sessions, how to protect routes with the session, and the **cross-origin cookie** gotcha.
The client (Vercel) and API (Render) live on different domains, so session cookies need
`sameSite=none` + `secure`, and CORS must be set up with credentials. That's the trickiest
part of this integration and where most people get stuck.

## Hosting

| Piece | Where | Note |
|---|---|---|
| Frontend (static PWA) | Vercel / Netlify | Free, always warm. |
| Express API | Render (free) | Spins down when idle → ~30–50s cold start on first open. Fine for personal use. |
| Postgres | Neon (free) | Durable free tier (doesn't expire like Render's own Postgres). |

Two-origin setup (client and API on different domains) → we'll deal with **CORS** and
cookie `SameSite`/`secure` settings. Good things to learn; I'll explain when we hit them.
